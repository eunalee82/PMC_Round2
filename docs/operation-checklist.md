# 운영 체크리스트 (행사 당일)

> 배포는 `docs/deployment-checklist.md`. 이 문서는 **당일 진행 담당자(감독관)** 용이다.
> 참가자 URL `https://pmc-round2.vercel.app` · 관리자 `https://pmc-round2.vercel.app/?admin`
> 32팀 + 테스트 팀 1 · 사건 15개 · 제한 시간 80분

## 0. 한 장 요약

```
T-60  관리자 로그인 → 상태 SCHEDULED 확인 → 진행 데이터 초기화
T-30  참가자 입장 시작 (팀 선택 → 수사관 3명 이메일 → 서약 → 대기실)
T-10  [팀 현황] 으로 32팀 입장·이메일 중복 확인 → 오선택 정정
T-0   [게임 시작]  ← 이 순간부터 80분, 서버 시각 기준
      진행 중: [팀 현황] 5초 갱신으로 모니터링
T+60  자동 종료(ends_at) 또는 [게임 종료]
      → [최종 랭킹 발표] 로 순위 공개
```

**중요**: 참가자 화면에는 최종 순위가 나오지 않는다. 랭킹은 감독관이 관리자 콘솔에서 발표한다.

## 2. T-30 · 참가자 입장

참가자 안내 문구:
> 팀을 고르고 **팀원 3명의 이메일**을 입력하면 입장입니다. 그 기기가 팀을 대표합니다.
> 기기를 바꿔야 하면, 새 기기에서 같은 팀을 누르고 **등록한 이메일 중 하나**를 입력하세요.

## 5. 진행 중 모니터링

| 화면 | 무엇을 보는가 |
|---|---|
| 관리자 콘솔 | `GAME STATUS` · `CONNECTION` · `TIME LEFT` · **[+5분 연장]**(장애 시 §8.4) |
| [팀 현황] | 팀별 제출 수·점수 (5초 갱신) — 진행이 멈춘 팀 발견용 |
| [최종 랭킹 발표] | 현재 순위 (발표 전에도 확인 가능) |

- 참가자 화면 좌측 패널에는 상위 팀 점수만 보인다(최종 순위는 아님).
- 제출은 **팀×사건 1회**로 서버가 막는다. 이미 제출한 사건은 다시 제출되지 않는다.

## 6. 연결 상태의 의미 (`CONNECTION`)

| 표시 | 뜻 | 조치 |
|---|---|---|
| `REALTIME · 실시간 전파` | 정상. 시작/종료가 즉시 전파 | 없음 |
| `POLLING · 5초 확인` | WebSocket 이 막혀 5초마다 확인 중. **진행에는 문제 없다** | 없음. 전파가 최대 5초 늦는 것뿐 |
| `OFFLINE · 서버 연결 없음` | 서버와 통신 불가 | 네트워크 확인. 복구되면 자동 재연결 |
| `LOCAL · mock 모드` | 비상 빌드로 실행 중 | 점수가 서버에 저장되지 않는다 — §8 참고 |

행사장 방화벽이 WebSocket 을 막는 경우가 흔하다. **`POLLING` 이면 그대로 진행해도 된다.**

## 8. 문제 상황 대응

### 8.1 팀 기기가 고장났다 / 배터리가 없다
새 기기에서 같은 팀을 누르고 **등록된 이메일 중 하나**를 입력 → 인계. 진행 상황(점수·제출)은 서버에서 그대로 복구된다.
새 기기에서는 서약을 한 번 더 받는다.

### 8.2 참가자가 팀을 잘못 골랐다 (시작 전)
그 기기에서 올바른 팀을 다시 등록하면 이전 팀은 자동 해제된다. [팀 현황] 에서 반영 확인.

### 8.3 참가자 화면이 "입장이 해제되었습니다" / "팀 인증이 만료되었습니다" 라고 한다

둘 다 **다른 기기가 그 팀을 인계했다**는 뜻이다(문구만 다르다 — 앞은 입장 화면, 뒤는 사건 제출 실패).
어느 기기로 진행할지 팀과 정리한 뒤 해당 기기에서 이메일로 다시 인계.

⚠️ **네트워크 장애와 헷갈리지 말 것.** "팀 인증이 만료되었습니다" 가 뜨면 [판단 제출] 버튼이 **비활성**된다
— 재시도해도 소용없다. 반면 네트워크 문제(§8.4)는 버튼이 다시 살아난다. **버튼이 죽어 있으면 §8.3,
살아 있으면 §8.4**로 판단한다.

원인은 대부분 **다른 팀원이 자기 기기에서 접속한 것**이다. 팀당 1기기 원칙을 다시 안내한다
(원격 참여 팀이 화면 공유로 진행하는 경우 특히 자주 발생한다).

### 8.4 네트워크가 끊겼다

⚠️ **끊긴 동안에도 타이머는 계속 간다.** 종료 시각(`ends_at`)은 서버가 정한 **절대 시각**이라 오프라인
기기에서도 카운트가 진행되고, 시간이 다 되면 그 팀은 사건 화면에서 자동으로 나가진다. 즉 **끊긴 시간은
그대로 그 팀의 손해**다. 이것이 네트워크 장애 대응의 핵심 판단 근거다.

**먼저 범위를 판정한다** — 관리자 콘솔 `CONNECTION` 을 본다.
- 관리자도 `OFFLINE` → **행사장 전체 장애** → (B)
- 관리자는 정상인데 특정 팀만 멈춤 → **그 팀 회선 문제** → (A)
  ([팀 현황] 5초 갱신에서 제출 수가 늘지 않는 팀으로 찾는다)

#### (A) 한 팀만 끊겼을 때 — 참가자에게 이렇게 안내한다

1. **그대로 두십시오.** 5초마다 자동으로 재연결을 시도한다.
2. **사건을 읽고 논의하는 것은 계속 가능하다.** 사건 본문·단서는 이미 기기에 받아둔 상태다.
3. 제출이 실패해도 **선택한 보기는 그대로 남아 있다.** 연결이 돌아온 뒤 **[판단 제출]을 다시 누르면 된다**
   (다시 고를 필요 없다 · 중복 저장되지 않는다).
4. **끊긴 상태에서 새로고침하지 말 것.** "PM보호국 서버에 연결할 수 없습니다" 화면에서 멈춘다.
   (이 화면에도 [다시 시도] 버튼은 있으니 잠기는 것은 아니다)
5. 복구된 뒤에도 화면이 이상하면 그때 새로고침 → 마지막 저장 지점에서 이어진다.

#### (B) 행사장 전체가 끊겼을 때

1. **아무 조작도 하지 말고 대기**하라고 방송한다 — 특히 **새로고침 금지**.
2. 관리자 콘솔 `CONNECTION` 이 `REALTIME` 또는 `POLLING` 으로 돌아오는지 본다.
   **`POLLING` 이면 정상 진행 상태다**(§6) — 복구된 것이므로 그대로 진행한다.
3. [팀 현황]에서 제출 수가 다시 늘어나는지 확인한다.
4. 장애 시간만큼 (C)로 연장하고 **연장 사실을 방송한다**(참가자는 시간이 늘어난 이유를 모른다).

#### (C) 시간 연장 — 관리자 콘솔 **[+5분 연장]**

콘솔에서 누르면 된다. 확인창이 한 번 뜨고, 필요한 만큼 **여러 번 눌러 쌓는다**(5분씩 누적).

- 참가자 화면의 남은 시간은 **Realtime 즉시 / 폴링 최대 5초** 안에 함께 늘어난다.
- ⚠️ **전 팀 공통으로만 늘어난다.** 특정 팀만 연장하는 기능은 없다(`games` 는 단일 로우).
  한 팀 때문에 늘리면 전체가 늘어난다 — 개별 팀 장애는 결과 정리 시 완료 시각 보정으로 처리한다.
- **진행 중(`STARTED`)일 때만** 눌린다. 종료된 게임은 서버가 거부한다 — 종료를 되돌리는 것은
  별개 절차다(§8.10 (5)). 이미 타임오버가 지난 뒤에 눌러도 **지금부터** 5분이 주어진다.
- 연장 후에는 **방송으로 알린다.** 참가자는 시간이 늘어난 이유를 모른다.

> ⚠️ 버튼이 "요청이 실패했습니다" 로 끝나면 마이그레이션 `0014_admin_extend_game.sql` 미적용일 수 있다.
> `node scripts/check-migrations.mjs` 로 확인한다.

**콘솔을 못 쓸 때만** SQL Editor 로 (§8.8과 동일한 경로):
```sql
update public.games set ends_at = greatest(ends_at, now()) + interval '10 min', updated_at = now() where id = 1;
select status, started_at, ends_at from public.games where id = 1;   -- 확인
```
- SQL 은 상태를 검사하지 않는다 — 이미 종료를 선언한 게임에 실행하면 **제출이 조용히 다시 열린다**
  (서버는 `now() >= ends_at` 로만 판정한다). 종료 후에는 쓰지 말 것.

#### 판단 기준 (권장)

| 상황 | 조치 |
|---|---|
| 1~2분 순간 끊김 | 조치 없음 — 자동 복구된다 |
| 특정 팀 5분 이상 | 전체 연장(C) 또는 결과 정리 시 참작. 어느 쪽이든 해당 팀에 알린다 |
| 전체 장애 5분 이상 | **장애 시간 + 5분** 연장(C) + 방송 |
| 20분 이상 복구 불가 | [게임 종료] → 그 시점 점수로 확정 → [최종 랭킹 발표]. `answers` 는 이미 서버에 있다 |

### 8.5 게임을 잘못 시작했다
**[대기 상태로 되돌리기]** → 확인창에서 **[취소]**(게임 상태만 대기로, 진행 데이터 보존)
→ 다시 [게임 시작]. 진행 데이터까지 지우려면 **[확인]**.

### 8.6 특정 팀 점수가 이상하다
SQL Editor 에서 `answers` 원본으로 재계산한다:
```sql
select * from public.answers where team_id = 'team07' order by submitted_at;
select public.recalc_team_progress('team07');
```

### 8.7 관리자 로그인이 안 된다
1. Authentication → Providers → **Email 제공자가 켜져 있는지** 확인(가장 흔한 원인)
2. 계정이 confirm 되었는지: `select email, email_confirmed_at is not null from auth.users;`
3. `admins` 등록 확인: `select * from public.admins;`
4. 화면에 표시되는 실패 사유를 그대로 읽는다(원인별 안내가 나온다)

### 8.8 최후의 수단 — SQL 로 직접 제어
관리자 콘솔을 못 쓸 때만. SQL Editor 는 `postgres` 권한이라 `is_admin()` 검사를 타지 않는다.
```sql
-- 시작 (80분)
update public.games set status='started', started_at=now(),
       ends_at=now()+interval '80 min', updated_at=now() where id=1;
-- 종료
update public.games set status='ended', ends_at=now(), updated_at=now() where id=1;
-- 대기로 되돌리기
update public.games set status='scheduled', started_at=null, ends_at=null where id=1;
-- 시간 연장 (10분)
update public.games set ends_at = ends_at + interval '10 min' where id=1;
-- 특정 팀 점유 해제 — 이메일까지 지우는 '완전 초기화'다. 보통은 §8.10 (3)-d 의
-- 가벼운 형태(claim_token·device_id 만 null)를 쓴다. 이메일을 비우면 인계 수단이 사라진다.
update public.teams set claim_token=null, device_id=null, entered_at=null,
       member_emails='{}', flags='{}' where id='team07';
```
> 점유를 해제해도 그 팀 화면은 즉시 반응하지 않는다 — **새로고침을 안내할 것**(§8.10 (3)-d).
> 참가자 클라이언트는 Realtime 또는 5초 폴링으로 이 변경을 받는다.

### 8.9 팀원이 원격이라 화면 공유로 진행한다

가능하다. 사건 화면의 전체화면은 **잠금이 아니라 가림**이라 화면 공유를 막지 않는다
(`src/components/game/capture-guard.js` — 전체화면을 벗어나면 사건 내용 위에 게이트가 다시 덮인다).

사전에 안내할 것:
- **조작·접속은 대표 기기 1대만.** 나머지 팀원이 자기 기기에서 접속하면 팀 점유가 넘어가 진행 중인
  기기가 튕긴다(§8.3). 화면 공유만 보고 논의한다.
- **회의 앱의 "컴퓨터 소리 포함"을 반드시 켤 것.** 15사건 중 7사건이 음성 단서라, 끄면 나머지 팀원은
  녹취를 들을 수 없다.
- **창(window) 공유가 아니라 "화면 전체" 공유로.** 창 단위로 지정하면 전체화면 전환 시점에 검은 화면이
  뜨는 사례가 있다.
- 순서: **회의 앱 화면 공유 시작 → 알림 팝업 끄기 → 브라우저에서 [전체화면으로 조사 시작]**.
- 팀명·시각 **워터마크가 공유 화면에도 보인다** — 정상이다. 미리 알려 당황하지 않게 한다.
- 중간에 게이트가 다시 뜨면 [전체화면으로 돌아가기] 한 번 누르면 된다. 진행 상태는 서버에 있어 유실되지 않는다.

⚠️ 원격 팀은 **회선이 셋이라 장애 확률도 높다.** §8.4 (A)를 그대로 적용하되, 끊긴 쪽이 **대표 기기인지
관전자인지** 먼저 확인한다. 관전자만 끊긴 것이면 게임 진행에는 아무 영향이 없다.

### 8.10 재시작 절차 — 오류가 났을 때

**원칙: 대부분의 오류는 새로고침으로 끝난다.** (1)이 99%다. (4)는 행사 중에 쓰는 수단이 아니다.

| # | 상황 | 조치 | 잃는 것 |
|---|---|---|---|
| 1 | 화면이 멈춤·깨짐 (기기 1대) | **새로고침** | 없음 |
| 2 | 기기 고장 / 브라우저 데이터 삭제 | 다른 기기에서 팀 선택 → 등록된 이메일 중 하나 → 인계 | 서약만 다시 |
| 3 | 특정 팀 상태가 꼬임 | 아래 (3) — 증상별로 다르다 | 없음 (점수 보존) |
| 4 | 게임 전체 재시작 | ⚠️ 아래 (4) — 진행 중에는 사실상 불가 | 큼 |
| 5 | 실수로 [게임 종료] 를 누름 | ⚠️ 아래 (5) — **복구 가능** | 없음 |

#### (1) 새로고침이 기본이다
`claim_token`·서약은 그 기기 localStorage 에 남고, 제출·점수는 서버에 있다. 새로고침하면
`resolveStep()` 이 서버 저장 지점으로 되돌린다. **사건 화면에서 새로고침해도 그 사건으로 돌아온다.**

#### (3) 특정 팀만 상태가 꼬였을 때 — 증상별로 조치가 다르다

**어느 경우에도 `answers`·`team_progress` 는 건드리지 않는다. 점수는 보존된다.**

| 증상 | 원인 | 조치 |
|---|---|---|
| a. 다른 기기가 팀을 가져갔다 / 이 기기가 팀을 놓쳤다 | 인계 발생 | **SQL 불필요** — 쓸 기기에서 팀 선택 → 등록된 이메일 하나 입력 |
| b. 화면만 꼬였다 (다음 사건으로 안 넘어감 등) | 클라이언트 캐시 | **새로고침** — 진행을 서버(`my_progress`)에서 다시 받는다 |
| c. 점수·진행 수치가 이상하다 | 집계 파생값 어긋남 | `recalc_team_progress` (아래) |
| d. 그 팀이 아예 입장을 못 한다 | 점유(claim) 꼬임 | 점유 해제 SQL (아래) |

**c. 점수 재계산** — `answers` 가 진실의 원천이고 `team_progress` 는 파생 집계라 언제든 다시 만들 수 있다.
```sql
select * from public.answers where team_id = 'team07' order by submitted_at;  -- 원본 확인
select public.recalc_team_progress('team07');                                  -- 재계산
```

**d. 점유만 해제 (권장 형태)**
```sql
update public.teams
   set claim_token = null, device_id = null, updated_at = now()
 where id = 'team07';
```
- ⚠️ **`member_emails` 는 지우지 말 것.** §8.8 의 전체 초기화 SQL 은 이메일까지 비우는데, 그러면
  **인계 수단 자체가 사라지고**(이후 기기 변경 시 증명할 이메일이 없다) 참가자 명단 기록도 없어진다.
  이메일까지 지우는 건 그 팀을 완전히 새로 등록시킬 때만 쓴다.
- ⚠️ **해제 직후에는 그 팀 화면이 반응하지 않는다.** `ownsTeam()` 은 로컬 저장값만 보고
  서버를 조회하지 않는다(`entries-server.js:95-97`). 그대로 두면 참가자는 계속 사건을 풀다가
  **제출하는 순간** `not_owner` 로 튕긴다 — 가장 나쁜 타이밍이다.
- → **해제한 뒤 반드시 그 팀에 "새로고침하십시오" 를 안내한다.** 새로고침하면 진행 조회
  (`my_progress`)가 토큰을 검사해 `not_owner` 를 던지고, 클라이언트가 팀 선택 화면으로 되돌린 뒤
  "입장이 해제되었습니다" 안내를 띄운다. 거기서 이메일 3개로 다시 입장하면 **점수 그대로 이어진다.**

#### (4) ⚠️ [대기 상태로 되돌리기] 는 리허설 전용이다 — 진행 중 누르지 말 것

버튼 라벨의 "(리허설)" 은 경고다. **어느 옵션을 골라도 32팀 전체가 재입장해야 한다.**

- **[취소] (진행 데이터 보존)** — 점수는 남지만 재입장이 더 어렵다:
  `status='scheduled'` 가 되면 모든 참가자 기기가 로컬을 지우고 reload 한다(`flow.js:169-173`).
  이때 소유 증명 토큰(`pmb.claim.v1`)이 지워지는데 **서버의 `claim_token` 은 그대로 남는다**
  (`0005_fix_admin_reset.sql:21-23`). `claim_team` 은 device_id 가 아니라 **토큰으로만** 소유를
  확인하므로(`0001_init.sql:203-206`) 전 팀이 **이메일 인계 절차**를 밟아야 한다.
- **[확인] (전부 초기화)** — `claim_token` 이 null 이 되어 재입장은 매끄럽지만
  `answers`·`team_progress` 가 **전부 삭제**된다(점수 소멸).

→ 즉 "점수 살리고 재입장 지옥" 또는 "재입장 매끄럽고 점수 전멸" 둘 중 하나다.
   **시작 직후(아직 아무도 제출하지 않음) 실수를 되돌릴 때만** [확인] 으로 쓴다.

#### (5) 실수로 [게임 종료] 를 눌렀을 때 — 리셋하지 말고 SQL 로 되돌린다

```sql
-- ⚠️ ends_at 을 반드시 미래로 함께 민다 (남은 시간을 실제 잔여분으로 계산해 넣을 것)
update public.games
   set status = 'started', ends_at = now() + interval '25 min', updated_at = now()
 where id = 1;
select status, started_at, ends_at from public.games where id = 1;   -- 확인
```

- `flow.js` 는 **`scheduled` 일 때만** 로컬을 지우고 reload 한다. `ended → started` 는 그 조건에
  걸리지 않으므로 **참가자 세션·토큰이 그대로 유지된다.**
- ⚠️ **`status` 만 바꾸고 `ends_at` 을 두면 안 된다.** [게임 종료]는 `ends_at` 을 `now()` 로 당겨 놓는데
  (`0001_init.sql:477`), 가드는 `isEnded() || isTimeUp()` 으로 판정하므로(`flow.js:186`)
  타임오버가 즉시 참이 되어 **참가자가 종료 화면에 그대로 갇힌다.**
- 참가자는 이미 종료 안내를 보고 종료 화면으로 이동한 상태다 → **"새로고침하십시오" 방송이 필요**하다.
  (상태가 돌아와도 화면은 자동으로 되돌아가지 않는다)

**새로고침 후 복귀 지점** — `resolveStep()` 실측 결과(11/11 통과, 2026-08-11):

| 그 팀의 진행 | 복귀 화면 |
|---|---|
| 사건이 남음 | 사건 화면 (남은 첫 사건) |
| 15사건 완주 · 임명 전 | 감독관 임명 |
| 임명 완료 · 레이드 전 | Final Raid |
| 레이드까지 완료 | 금배지 · 종료 안내 (원래 자리) |

## 10. 알려진 제약 (참가자에게 안내할 것)

- 팀당 1기기. 여러 기기에서 동시에 같은 팀으로 진행할 수 없다.
- 한 번 제출한 사건은 수정할 수 없다.
- **네트워크가 끊긴 동안에도 남은 시간은 계속 줄어든다**(종료 시각은 서버가 정한 절대 시각). 장애 시
  운영진이 전체 연장 여부를 판단한다 — §8.4 참고.
- Stage 2 사건은 **임시 콘텐츠**다(화면에 `임시 데이터` 표시). 확정 콘텐츠로 교체 예정.
- 최종 순위는 참가자 화면에 표시되지 않는다.
